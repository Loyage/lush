创建 worktree-service：调用 service_construct，参数 template="worktree-service"、name=<worktree 短名，必填>、goal=<在这个 worktree 上要长期做的事，可选>、variables={"path": "<worktree 的绝对路径>"}；命令行等价于 `lush service construct <你的 SID> worktree-service --name <短名> [--goal '<目标>'] --vars '{"path":"<绝对路径>"}'`。path 是本模板唯一声明的变量，必填且不可变：必须是「已经存在」的绝对目录。通常 project 已经在派活前用 `git -C <仓库> worktree add <目录> -b <分支>` 串行建好了它（goal 里带 `worktree=<目录> branch=<分支>`），dev-task 只需把这对值绑到本节点上；只有 goal 没给 worktree 时，dev-task 才先自己 `git worktree add` 再建本节点。不是绝对路径、不存在或不是目录时创建直接失败（-32602）。它绑定的就是这个 worktree：path 同时是该节点上所有 task 的工作目录。singleton=false，但约定是「一个 worktree 一个节点」：创建前先看 children，path 相同的就复用。它是叶子节点（child_templates 为空）：创建后用 `lush task construct <它的 SID> --goal '<要改什么>'` 派活，再结束本轮——它结算时你会被唤醒并拿到结果，它会如实报出改动、分支与验证，但**不替用户决定要不要合并**。它的回收由你的回收 task 执行：用户同意后先 `lush service stop` 这个节点，再删 worktree 与分支（它的 system_prompt 里写着自己的析构契约：回收时按它 state 里的 path / 分支 / 主仓库 / HEAD 删，四项要与现场一致），所以在派给它的 goal 里也点一句「把你的 path / 分支 / 主仓库 / HEAD 写进持久 state」。
