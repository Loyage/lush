创建 dev-task：调用 service_construct，参数 template="dev-task"、name=<任务短名，必填>、goal=<目标，可选>、variables={"title": <一句话摘要，必填>, "detail": <详情正文，可选>}；命令行等价于 `lush service construct <parent> dev-task --name <短名> --goal '<目标>' --title '<一句话摘要>' [--detail '<正文>']`。三个字段的规矩：name 是不可留空的英文标识符 ^[A-Za-z][A-Za-z0-9_-]*$、不超过 64 字符、不含空格——它同时就是这个服务的服务名，用来命名相关的 worktree / 分支；title 是不可留空的单行摘要（≤200）；detail 是详情正文（可多行、可空、≤20000）。格式不合规、缺少 name 或 title 时创建直接失败（-32602）。dev-task 只允许创建一个子模板：worktree-service。它管两个阶段：开发 task（把一件工作派给 worktree-service 在一个独立 worktree 里用 agent 做）与回收 task（goal 以「回收」开头：核对 worktree-service 的 state → 自检 → `lush service stop` 那个节点 → 删除 worktree 与分支）；用户同意回收时在同一个节点上再开一个回收 task 即可，不要自己删 worktree。

worktree 归谁建：**project 在派开发 task 时会把 `worktree=<目录> branch=<分支>` 写进 goal**——它已经串行建好了（多路并行时若每路各自 `git worktree add`，同名分支与目录会互相撞车），dev-task 直接复用、不再新建。只有 goal 里没有 worktree、且没有「不要开新 worktree」「就在当前分支 / 主工作树上改」这类例外时，dev-task 才自己 `git worktree add` 建一个。所以调用方要自己建 worktree 时，就在 goal 或 detail 里写明工作方式与路径。创建后它不会自动干活：用 `lush task construct <它的 SID> --goal '<要改什么、怎么算完成>'` 派 task 给它。
