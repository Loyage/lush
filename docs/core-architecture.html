LUSH CORE ARCHITECTURE · VERSION 2

从用户 Intent，走到可以亲眼验收的精确结果

Lush 是项目级多 Agent 开发与信息集成工具。模型负责理解、实现和综合；确定性 runtime 负责编排、依赖、资源、持久化与 Git 安全；用户最终验收固定 commit，而不是模糊的“任务完成”。

核心公式：Intent-first + Candidate-first，Branch-backed。

一、四个中心，各司其职

用户目标中心

Intent

保存用户原话、目标分支、流程模式与当前交付状态。所有计划、工作、反馈和候选版本都回到同一个 Intent。

执行中心

WorkItem + Run

WorkItem 是稳定工作节点；Run 是一次真实模型调用。重试、换模型和唤醒形成新的 Run，不覆盖历史。

信息集成中心

Artifact

代码提交、测试证据、报告、发现、风险和摘要都是结构化 Artifact；用户无需阅读所有 transcript 才能理解成果。

验收中心

Review Candidate

Candidate 固定 integration branch 上的精确 commit，绑定基线、前后对照、测试证据和 HTML 报告。

代码交付中心

Branch + Commit

Branch 负责隔离、集成和恢复，Commit 负责不可变身份。Git 是交付基础设施，不要求普通用户用提交拓扑理解目标。

人工控制中心

Decision

只有影响行为、存在歧义、发生冲突或最终交付时才请求用户决策。普通状态更新由 Event 与投影生成。

三、为什么不是 Branch-first

Branch 能准确回答

  1. 代码从哪里分出
  2. 有哪些 commit
  3. 是否领先、落后或分歧
  4. 能不能安全合并
  5. 如何恢复工作现场

用户验收真正要回答

  1. 功能是不是我想要的
  2. 修改前后有什么差异
  3. 测试和真实运行是否成立
  4. 有哪些风险和未完成项
  5. 批准的是不是刚刚看过的版本

结论：Branch 仍是 Git 子系统的核心，但产品主线以 Intent 和 Review Candidate 为核心。Candidate 使用不可变 commit 防止 branch 在验收后继续移动、夹带用户未看过的内容。

四、双轴模型

产品轴
Intent └─ Plan revision └─ Work DAG └─ Artifacts └─ Review Candidate v1/v2/… └─ Decision
Git 轴
Target Branch └─ Intent Integration Branch ├─ Worker Branch A ├─ Worker Branch B └─ Worker Branch C Candidate → exact integration commit

五、核心实体与边界

实体负责不负责
Intent原始目标、模式、目标分支、整体状态单次模型调用细节
Plan版本化拆解、依赖、验收标准、风险调度进程与 Git 操作
WorkItem一块稳定目标及完成条件把多次重试压成同一次执行
Run一次 provider invocation、模型、成本、结果和错误长期业务身份
Artifact结果、commit、报告、证据、发现和风险控制任务生命周期
Review Candidate固定 commit、基线、报告和用户验收状态可变 branch 的未来内容
Decision高风险计划、实质歧义、冲突与最终接受普通进度通知
Event不可丢失的审计与恢复事实直接充当用户摘要

六、Plan 编译与并行调度

Planner 做语义判断；runtime 做确定性编排。Planner 一轮写完后，Plan Compiler 在事务中建立工作节点和依赖，不再经过 scheduler agent，不消耗额外模型调用，也不存在全项目 scheduler 批次锁。

Control lane

Planner、综合与冲突分析使用独立槽。长时间 worker 无法饿死新输入规划。

plannersynthesizerconflict analysis

Execution lane

Worker、Research、Test、Verifier 使用执行槽；依赖未满足和等待用户时不占槽。

workerresearchtestverifier

依赖与代码基线分离

depends_on: [work-3, work-5] // 运行前置条件，可有多个 code_base: work-3 // 代码从哪里开始，最多一个 integration_target: intent-42 // 最终聚合到哪里

七、结构化信息集成

每个 Run 的最后输出形成 Artifact。文本仍保留，但核心投影使用统一 envelope，便于 reducer 持续生成 Intent Digest。

{ "outcome": "success", "summary": "完成了什么", "changes": [{ "area": "src/auth", "description": "新增刷新逻辑" }], "evidence": [{ "command": "bun run test", "exitCode": 0, "summary": "344 passed" }], "decisions": [], "risks": [], "artifacts": [{ "kind": "commit", "value": "abc123" }], "followups": [] }

代码 reducer 聚合事实；只有语义冲突、计划重写或最终叙述需要时才启动 synthesizer agent。

八、验收候选生命周期

preparing→ready→accepted→integrated
ready→changes_requested→Candidate v2
ready→rejected / superseded

Candidate 创建时同时固定 integration commit 与 baseline commit。Verifier 在两边运行同一验收场景并生成自包含 HTML 报告。接受前 runtime 再次校验 branch tip 仍等于候选 commit；若已经移动，必须生成新版本。

十、安全与恢复原则

项目级作用域

一个 daemon 绑定一个 canonical 项目目录，状态固定在项目的 .lush。

短期凭证

Agent token 只在当前 invocation 有效，数据库只保存 SHA-256。

未知副作用不重放

崩溃后的 running Run 标记失败，由用户检查现场并明确重试。

Git 写操作串行

不做 shell 插值；compare-and-swap 与每次重新校验防止静默覆盖。

验收绑定 commit

用户接受的是不可变树；branch 漂移后旧批准不得复用。

历史与磁盘分离

Run、Artifact、Event 可长期保留；worktree 和 branch 按安全门独立回收。

十二、当前实现与演进边界

现有 SQLite、项目 daemon、worktree 隔离、事件审计、短期 token、恢复策略和最终用户批准继续保留。迁移采用加表/加列与兼容 RPC：Task 暂时作为 WorkItem 投影，新增 agent_runs、artifacts 与 review_candidates；旧 task/spec/branch 历史仍可读取。

架构判断标准不是“层数越少越好”，而是：语义判断交给模型，确定性工作交给 runtime；用户围绕目标和结果行动，Git 围绕安全和恢复行动。
