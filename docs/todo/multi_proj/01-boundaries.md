# 多项目身份与安全边界

本篇为[多项目工作台规划](README.md)定义目标边界与待确认的产品决策，面向设计及服务端实现者。现有入口在 `src/ui/web/server.js`（`createProjectHost` / `startWeb`）、`src/ui/launcher.js` 与 `src/config.js`。

## 核心不变量

- 一个 canonical 项目路径仍对应一个 daemon、独立 `<project>/.lush/`、socket、Git 工作区及项目级配置；Web／桌面仅是多个项目的宿主与视图，不托管跨项目业务事实。
- 同一工作台可连接 A 和 B；A 的执行不因用户查看 B 而暂停。任意两个标签页可分别停留在 A／B，也可同时看 A 的不同任务。Task、Notice、Draft 等数字 ID 仅在其项目内有意义。
- **项目身份必须从请求路由确定并由服务端校验**；不能从 Web 进程全局 `binding`、另一标签页最后选中的项目、轮询结果或请求体里不受约束的路径推断。读和写、报告与预览、历史与流式阅读都遵守同一规则。
- 公网模式对每次项目访问重新执行现有认证及 `web.json.projects` canonical 白名单校验；本机模式也不能让不明确项目的旧页面把操作落到另一项目。不把项目绝对路径放在可伪造的 HTTP 动作参数中当作授权。

## 建议的宿主模型（待确认）

全局宿主维护按 canonical 路径索引的连接集合；每项持有本项目的 `Config` / `UIClient` 与连接状态。同一项目的并发打开只做一次启动／连接尝试（single-flight）；连接失败只影响该项目，可显式重试，不清除其它连接或覆盖上一次成功选择。项目注册表只存路径、展示顺序及上次打开位置等**界面元数据**，不复制 Task 或 `.lush` 数据。复核项目目录是否仍存在、canonical 路径是否变化时，要显式显示错误，不静默绑定别的目录。

建议给全局页面和 API 采用项目范围的稳定路由（示意：`/p/<project-id>/`、`/p/<project-id>/api/action`、`/p/<project-id>/api/task/1`）；服务端把不透明 ID 解析成已登记且允许访问的 canonical 路径，不能把 URL 片段直接当文件路径。静态 asset 和随代码发布的帮助文档可继续是宿主级资源。所有项目数据路由（包括 report HTML、问卷预览与读请求）需在路由识别后才获取所属 `client/config`；action 的项目身份在一次请求中冻结，不因别的请求打开项目而改变。明确缺失／未知／失效身份时返回错误，**绝不回退到“当前项目”**。

显式 `--project` 的单项目 Web 和 CLI 默认向上发现规则先保留；旧全局 `/api/launcher/select`、无前缀 `/api/action` 等接口的迁移行为必须明文定义，不能在仍有旧页面时让无身份写操作指向新项目。优先让全局无前缀写路由拒绝并提示刷新／升级；若需短期兼容，只能绑定到不会变更且可验证的项目身份。路由 ID 的生成与持久化细节留在协议设计阶段定稿，要求抗冲突、同一路径稳定、不同 canonical 路径不可混同。

## 产品选择：实施前请用户确认

1. “打开项目”是否意味着登记到左侧列表并按需启动 daemon？“从列表移除”是仅隐藏入口、断开 Web 连接，还是也停止 daemon？**建议默认只移除入口、不停止 daemon**，停止仍走显式项目命令。
2. 桌面窗口、浏览器标签及设备是否各自独立保持当前项目和页面？**建议独立**，不通过全局 `last_project` 实时同步。恢复上次项目只决定新窗口首次落点，不覆盖已经打开的页面。
3. 初版是否只展示已打开项目的简短状态／待决数，还是要求跨项目总待办与跨项目通知？**建议先做有界摘要，不做全局待办或统一决策动作**。
4. 本地项目添加是否允许任意绝对目录、公网是否仅能从白名单添加？**建议保持现有边界**；尤其不能把公网的白名单退化为仅控制选择器列表。
