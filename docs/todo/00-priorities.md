# 优先级与实施前决策

本文是对五份审查报告的综合判断，帮助维护者选择先做什么，而非自动批准方案。基线、证据分级与验证汇总见[审查索引](README.md)；条目事实仅在各专题维护。

## 总体判断

项目已有较扎实的安全基础：独立 worktree、人工最终批准、固定提交交付、invocation 凭证轮换、失败不重放、有界首页读面及较完整的回归测试。本次全量测试通过，改进重点不是换框架或增加业务实体，而是**补齐异步操作之间的身份与状态约束，并让异常路径与正常路径一样可靠**。

多处现象具有共同原因，但不宜用一个“大重构”解决：

- 操作开始时校验正确，不代表异步等待后仍正确：清空、归档、写后导航各需自己的重检或身份约束。
- 固定一个 ID / commit，不等于固定实际使用的资源：页面项目 binding、verifier 的工作树、外部切换的 HEAD 都要区分。
- 返回结果有界，不等于内部读取与排队有界：调度依赖、inbox、RPC 写队列和图读取成本分别需要预算。
- 单元测试全绿，不等于部署与真实 UI 已验证：保留快速测试，再补少量契约、竞争时序和真实客户端验证。

## 第一批：优先评审的五项风险

| 建议顺序 | 条目与依据 | 为什么优先 | 实施前必须明确 |
|---|---|---|---|
| 1 | [S-01 · 项目错投](03-security-boundaries.md) | 旧页面的合法操作可落到另一项目；取消/删除/合并的对象身份最关键 | 窗口同步切项目，还是各自独立绑定？最低要求是拒绝身份不符的操作 |
| 2 | [R-01 · 清空竞态](01-runtime-persistence.md) | 已成功创建的新草稿会被正在完成的清空删除 | 清空期间暂拒写入，还是只清请求时快照？ |
| 3 | [G-01 · 活动工作区归档](02-git-worktrees.md) | branch=null 的 planner 仍在用 anchor，现有检查未覆盖 | 活动资源使用者的统一口径；保留“仍在使用就拒绝”而非自动取消 |
| 4 | [R-02 · 陈旧锁双持有](01-runtime-persistence.md) | 项目单 daemon 是调度、数据库和 Git 队列的共同前提 | 在零第三方 runtime 依赖和支持平台下采用什么互斥原语？ |
| 5 | [G-02 · 验收树不一致](02-git-worktrees.md) | pass 证据可能来自未提交内容，却标记为固定 commit | 校验共享树，还是单独固定检出？验收期间树变化如何报告？ |

S-01、R-01、G-01 已由协调者独立再次复现；R-02 是锁原语交错复现，不是已观察到生产双 daemon；G-02 是实际文件读取配合 mock verifier 的证据路径复现。Candidate 属于保留的兼容交付路径，是否经常使用可影响 G-02 排期，但不能改变其证据含义。

## 第二批：小范围、直接改善日常使用

| 候选 | 投入 | 预期价值 |
|---|---|---|
| [U-01 / U-02 · 批量提交与草稿失败保留](04-web-desktop-experience.md) | S + S | 不遗漏当前要求，网络失败不丢正在编辑的文字 |
| [U-04 / U-05 · 迟到导航与中文组词](04-web-desktop-experience.md) | S + S | 不抢回用户已切走的页面，不把输入法回车当最终确认 |
| [G-05 · Candidate baseline 回收](02-git-worktrees.md) | S | 长运行会话不积累可回收检出，cleanup 报告真实资源状态 |
| [E-02 · 文档命令入口](05-testing-maintainability.md) | S | 照着文档运行的命令能到达现有实现 |
| [S-06 · 登录回跳规范化](03-security-boundaries.md) | S | 封闭外站跳转边界；不夸大为口令泄露或认证绕过 |

以上为候选组合，不是“可以无审批直接改”的授权。尤其提交集合、草稿冲突的产品语义仍要在实施前约定；先加失败回归，再做最小修改。

## 第三批：长时间运行与规模增长

- **恢复闭环**：[R-04](01-runtime-persistence.md) 修复无主 running Run；[G-04](02-git-worktrees.md) 让部分归档可诊断、可显式继续。两者都不能用自动重放未知副作用来掩盖错误。
- **资源与模型成本**：[R-05 / R-06 / R-07](01-runtime-persistence.md) 分别处理容量背压、消息输入预算和全历史热读；[S-05](03-security-boundaries.md) 处理传输积压。它们是不同层的预算，不应合成一个难以解释的全局硬停开关。
- **图性能**：[G-06](02-git-worktrees.md) 减少后台重复 Git 查询，[U-06](04-web-desktop-experience.md) 减少前端重复 DOM 构造，[E-06](05-testing-maintainability.md) 留存可比较的测量。三项属于同一性能主题的不同层，不重复宣称同一份耗时收益。
- **跨客户端一致性**：[U-03 / U-07](04-web-desktop-experience.md) 分别解决旧 Notice 页状态与桌面偏好；不同于 S-01 的项目身份安全问题。
- **部署与信任边界**：[S-02 / S-03 / S-04](03-security-boundaries.md) 补来源矩阵、IPC sender 校验和代理限流；必须保留已明确支持的代理/webview 场景，不能仅凭 HTTP mock 声称浏览器利用成立。

## 已知限制：单列评估，而非当作新漏洞

- [R-03 · 宿主强杀后的 agent 清理](01-runtime-persistence.md)：恢复文档已披露 SIGKILL 可遗留进程。父进程死亡监护值得考虑，但属于增强现有保证；不得擅自按历史 PID 杀进程。
- [G-03 · 外部 checkout 竞态](02-git-worktrees.md)：README 已要求合并期间不要让其它程序修改同一工作树。复现证明越过这个使用前提会产生错误成功；可以先改善诊断，但完整防护涉及协作锁或交付架构，不能承诺“再检查一次就彻底解决”。

两项按潜在影响标 P1，**不表示与前五项同样需要立即修复**。若团队能够遵守现有边界，可先保留运行提示；若要支持更强异常恢复或多人同时操作，则需显式提升保证。

## 实施如何继续并行

下面是建议文件所有权，不创建新任务、不提前修改接口；实际开工前仍以[模块地图](../engineering/modules.md)为准。

| 可并行工作包 | 主要所有权 | 避免冲突的条件 |
|---|---|---|
| 清空 / 恢复 / 调度 | `core/project/`、对应 Store 模块 | R-01 与 R-04 都碰 lifecycle，交给同一 owner；锁原语 R-02 可独立验证 |
| Git 资源生命周期 | `core/workspaces/`、project 的 branches/verify | G-01/G-02/G-04/G-05 先约定资源使用者与回收接口；不要四人同时改 worktree/cleanup |
| Web host 安全 | `ui/web/server.js`、RPC、桌面 IPC | S-01/S-02/S-04/S-06 共用 server，由同一 owner 排序；项目身份协议先与前端协商 |
| 前端可靠性 | composer、drafts、notices、dialog | U-01/U-02 与 notice 修复可分文件并行；共享 api/navigation 变更先协商 |
| 质量门禁 | `test/helpers.js`、CI、docs-check、性能脚本 | E-01 先统一测试隔离；E-03/E-04/E-05/E-06 可分阶段，不一次引入多套测试框架 |

[E-01～E-06](05-testing-maintainability.md)是上述工作的验证基础，而非另一个产品重写计划。实施第一批时优先补确定性交错测试；真实浏览器 / Electron 冒烟和最低版本矩阵的依赖、成本及支持范围由维护者决定。

## 收口标准

一条候选进入“已完成”前，至少应有：维护者确认的语义、可重复的回归测试、既有安全门未退化的证据、必要的文档/API 契约更新，以及明确的剩余风险。未验证的假设先做实验，不因报告中出现过就直接当成需求。
