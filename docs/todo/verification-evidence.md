# 结构化验收证据

本条面向验收流程与结果读模型维护者，目标是让用户区分“验收任务执行完了”和“改动已经验证通过”。入口为 `src/core/project/scheduling.js`、`src/core/project/lifecycle.js` 与 Candidate 相关模块。

## 状态与优先级

- 优先级：P1，在一致性修复和测试基线恢复之后推进。
- 状态：设计建议，尚未实施。
- 依据：源码审查，不是对现有报告质量的全面评估。

## 当前限制

正常 provider invocation 返回后，runtime 生成 `run.result` Artifact，payload 中 `outcome` 固定为 `success`，而 `changes`、`evidence`、`risks` 等字段是空数组。

这里的 success 代表调用正常返回，不能直接等同于需求满足或测试通过。

Candidate 当前进入 `ready` 的主要条件是 verifier task 完成且 HTML 报告存在。报告可能写明测试失败、部分验证或无法验证，因此 ready 也不能作为质量通过结论。

## 建议方向

- 把执行状态和验收结论分开表达。
- 证据建议包含被测 commit、基准 commit、运行命令、退出码、结果摘要与报告引用。
- 显式记录失败项、未验证项、基准本来就失败的项目以及残余风险。
- 对 provider / agent 提交的结构化结果做格式和大小校验，不把模型自述当作独立验证事实。
- 保留自包含 HTML 报告作为人类阅读入口，结构化证据作为可查询和展示的数据来源。
- 继续保留人工接受，不让自动结论直接触发目标分支合并。

字段、存储方式、结论枚举和失败时能否人工接受都属于接口或产品决策，实施前应确认；不默认增加新的业务实体或重写旧记录。

## 验收标准

- [ ] 用户能区分执行完成、验证通过、验证失败和未验证。
- [ ] 每份证据明确绑定被测提交与基准，不能被分支后续推进替代。
- [ ] 仅有报告文件不再被展示成“测试通过”的充分依据。
- [ ] 失败或不完整证据不会被统一包装成成功结论。
- [ ] 旧 Artifact 和旧 Candidate 仍可读，缺少证据时明确显示未知。
- [ ] 补齐通过、失败、部分验证、无报告和基准失败场景的测试。
