# 控制快照与日志读取成本

本条面向 Web 读模型与会话投影维护者，目标是让运行成本不随全部历史数据线性放大。入口为 `src/ui/client.js`、`src/ui/web/assets/refresh.js`、`src/core/project/status.js` 与 `src/core/transcript.js`。

## 状态与优先级

- 优先级：P2。
- 状态：待测量与优化。
- 依据：源码路径明确存在；尚未做大规模数据压力测试，不宣称已有具体延迟指标。

## 快照轮询

`UIClient.snapshot()` 每次请求多个读模型，并循环分页读取全部 task。前端常规刷新还会调用多个列表渲染函数，`system.status` 同时返回完整 Agent 配置。

长期积累任务后，请求量、响应体积和渲染成本会增长，即使用户当前只看一个局部视图。

建议先做有界读取，不把引入 WebSocket 作为前提：

- 首页返回摘要、活动任务和最近记录。
- 历史列表按需分页，详情按需读取。
- Agent 完整配置在设置页加载，避免每轮状态请求重复传输。
- 引入 revision 或变更游标，跳过无变化的数据和视图刷新。
- 保留当前分支图最小刷新间隔与最大陈旧时间的约束。

快照字段、分页和刷新策略涉及公共读模型与 UX，具体方案应确认后实施。

## 日志读取上限

`recordsOf()` 在读取文件之前只检查已累计的预算，随后使用 `fs.readFileSync()` 读取整个文件，再累加字符串长度。

因此当前声明的 8MB 限制不能限制单个超大文件的读取量；字符串长度也不等于 UTF-8 字节数。同步读取和解析还会占用 daemon 主线程。

建议：

- 按字节预算进行分块读取，避免先把整个文件读入内存。
- 用文件标识、偏移及变更信息增量解析。
- 缓存用量聚合，避免轮询时从头扫描日志。
- 保留 JSONL 尾部半行容错，正确处理多字节字符、文件追加与截断。

## 验收标准

- [ ] 建立小、中、大历史任务数据集，记录快照大小、请求耗时与渲染成本。
- [ ] 首页常规轮询不再读取全部历史任务。
- [ ] 大日志请求的实际读取字节数受预算约束，包括单文件超过预算的情况。
- [ ] 增量读取与全量解析结果一致，追加或截断后无重复和遗漏。
- [ ] 日志读取期间其它 RPC 仍保持可接受响应，阈值在测量后确定。
- [ ] 截断和分页状态在 UI 中明确显示，不把局部数据表现为全部历史。
