# 归并合并方案：算法与持久协议

本篇定义 W205／D482 的目标技术协议，**不等于首版全部能力或当前 API 契约**。不新增核心业务实体；归并运行、节点与成员都是父 Worker 的交付技术记录。固定批次与协议v3已实现。本篇最终命令验证与验证排程槽描述保留为旧command协议／历史方案；新Agent模式不再强制最终验证快捷指令，实际挂载、默认及在途兼容以[实施接缝](merge-convergence-implementation.md)为准，模块见[Runtime地图](merge-convergence-runtime.md)。动态扩批、单目标验证晋级槽、自动语义风险识别与预算调优仍是后续设计，不应当作既有功能。

阅读路线：[产品与理念](../design/merge-convergence.md) → **算法与架构（本篇）** → [异常与迭代](merge-convergence-cases.md) → [实施与验证](merge-convergence-rollout.md)。

## 1. 四个对象边界

| 技术记录 | 必须固定的内容 | 不代表什么 |
|---|---|---|
| 交付成员 | Worker ID、轮次、delivery_id、source SHA、增量基点、真实 parent ID/ref、入队序号、来源测试摘要 | 不是当前可变 branch tip，也不是整段 Worker 历史 |
| 归并运行 | parent、目标基线 B、成员有序清单、generation、拓扑、协议/合并策略版本 | 不是新的父 Worker，不改变分支谱系 |
| 归并节点 | 左右子节点或叶子、输入树、基线 B、输出树/固定提交、修复与验证证据 | 不是进入 main 的事实 |
| 发布收据 | 精确落地 L、单父 B、最终树 T、完整成员清单摘要、目标检出身份与验证证据 | 不是凭标题或等价树猜出的成功 |

持久化建议使用 `delivery_runs`、`delivery_nodes`、`delivery_members` 技术表，归属父 Worker；`tasks.reservation` 的新 version 保存当前 delivery 与运行关联。不把共享批次 JSON 复制到每个 Worker 后分别更新。成员当前有效归属有唯一约束，节点内容不可变，状态更新带 generation/CAS。

事实在 SQLite 事务中保存，Message/Event 只是通知。生成和发布均有精确收据；来源映射、修复范围与测试摘要进入 Event/Artifact。新轮次不得覆盖旧轮次，历史 version 1/2 行与事件不改写。

## 2. 从源历史得到“本轮增量”

不得把多个源分支的完整树逐个覆盖到 main，也不能只用 `git merge-base(source, main)` 处理历次 Squash。必须给每个成员建立可追溯的增量基点 E：

- 首轮普通分支尊重真实共同祖先及 Git 多基点语义；简单单基点场景可取创建基点，不能把任意 `base_commit` 当作总是正确的共同祖先。
- 后续轮次优先采用有精确收据的上次源提交 S₀：证明 S₀ 仍是当前 S 的祖先，上次落地 L₀ 仍在当前父历史中，只提交 S₀ 之后的变化。
- 若已有成功父同步收据，可采用其记录的、同时属于源与父历史的更新共同基点；必须证明不会跳过源侧尚未交付的改动。
- 历史 `code` 依赖的来源只有上游已经在同一目标落地、其基线映射可证明时才准入；不借本功能新增依赖写入口。
- 缺失映射、祖先被外部重写、混入无法归属的来源时暂停，不能以 patch-id、树相等或标题猜“已交付”。

对固定父基线 B，叶子归一化为 `Tᵢ = merge3(Eᵢ, tree(B), tree(Sᵢ))`，由经过能力检测的 Git 三方对象合并完成。真实历史需要多 merge-base 时尊重其算法；等价来源基点使用明确固定的基点参数，不伪造真实祖先。

无文本冲突不自动唤醒原 Worker；产生冲突、已知接口迁移/整体改名/架构重构，或测试暴露组合适配问题时进入专用整合路径。风险识别与测试都不保证捕获全部语义错误，证据必须保留这个限制。

**新批次不能沿用现有“单源树等于落地树”的假设。** 多个成员共同形成 T，通常 `tree(Sᵢ) ≠ T`。来源基点凭“该固定增量已被纳入该次受检发布”的成员收据成立；适配改变来源内容时记录差异，不声称 byte-for-byte 相等。父同步、`squashedLanded`、迭代状态与资源回收判断必须同时适配此映射。

## 3. 配对与树形归并

归一化叶子用合成提交表示，父为 B；内部节点在私有对象空间合并输出，不修改原分支。左右节点必须具有同一 B、同一协议与互不重叠的 delivery 成员集合：

```text
combine(left, right):
  assert compatible_baseline_and_policy(left, right)
  assert disjoint(left.members, right.members)
  T = merge3(tree(B), left.tree, right.tree)
  if conflict: request_isolated_integration_for_this_node()
  else: persist_exact_node_result(T, left, right, B)
```

同一 B 上的归一化树各自包含 B，因此内部归并明确使用 B 为共同基点，不能让人工修复提交的祖先形状改变实际增量语义。源共同祖先检查与内部统一基点是不同步骤。

按入队序号稳定划分相邻片段，对大小相近的片段两两归并，奇数尾项直接保留。子节点已固定后不因线程完成顺序换左右；每个节点包含固定成员与拓扑，重复调度命中同一节点，不产生 A→B、B→A 两套结果。

合并不满足结合律：换拓扑、左右、成员或修复内容都是新候选，必须生成新 generation 并重新验证。禁止宣称与任意串行顺序等价；不允许 runtime 用 `ours/theirs` 静默化解冲突或丢掉成员。

初始调优候选：每批最多 8 项、忙时最多 200ms 形成窗口；独项且目标空闲时立即准备。窗口或容量达到即封闭成员，有就绪结果即可发布，不等二的幂、不等整个队列清空。这些是待基准验证的默认候选，不是已证明最优或产品完成时限。

批次未封闭时可合入新的兼容节点；封闭后新成员进入下一批。拆分、撤回、目标变动产生新运行/版本，保留原成功子节点，只按严格证据复用。长期积压不会把归并树无限变成一个全项目“大提交”。

## 4. 两种槽与一个短写门

- **准备槽**：项目内有界并行，处理对象合成、专项验证与整合调用；CPU/内存/磁盘与 Agent 调用分别限额。为交付预留调用机会，但不能耗尽开发槽；并发为 1 时也能顺序完成。
- **最终验证排程槽**：每父目标至多一个候选进入针对当前 B 的最终验证，防止互相落地反复使证据过期。它只约束交付晋级，不冻结父开发或新建指令；普通写入仍可使候选失效。
- **发布写门**：仅在真实父 invocation 已退出、清洁度和所有固定条件通过后取得，与父开发、同步、向上交付、Hook 命令互斥；不跨 Agent 或测试进程持有。

最终验证失败或待决立即释放晋级槽；后面已就绪批次可以先晋级。验证有明确超时、资源错误与取消结果；不能无限占槽。候选失效后保留其原入队优先级，并有界让位，避免重试活锁。冲突修复、基线重建与测试诊断分别设次数/时长/费用预算，超限转可见待处理，不自动无限付费。

不同父目标可独立晋级；同一项目持久化、ref/worktree 创建销毁和真实发布仍通过 Workspaces 串行写门。为真并行增加显式“固定对象计算”边界，只允许不可变对象生成与独立检出测试，不修改 ref/index，不把原 `exclusive` 一删了之。

## 5. 专用整合 Worker

仅 runtime 可创建拟议 `task_kind='integration'` Worker，挂在真实父 Worker 下，关联固定节点与尝试，拥有注册过的私有 scratch ref/worktree。原成员不重挂到它下面；它不是旧 merge 身份，也不走普通 child 自动 Squash。

授权只允许修改自己的组合资源、读取本项目固定输入、提交修复与请求 Notice；不能推进父或源 ref、改自动链、给无直接权限的源 Worker 发普通消息。runtime 用受控上下文传入来源目标、报告、两侧增量/改名、精确证据，不复制来源会话的凭证，不冒充某个源 Worker 的身份。

整合 Worker 创建时冻结直接父的有效运行配置，main/owner 无显式覆盖时沿用设备默认与既有合法连接选择；不随机借某个源 Worker 的付费账号。用量计在辅助身份上，批次摘要引用它，不重复累加到每个成员；调用预算不足明确等待。

完成产物必须保留固定组合输入的来源证据与输出树，核对超出来源范围的修改，歧义问用户。无冲突但涉及公共接口迁移时仍需语义审查；不能只读冲突标记。修复完成后专项实际跑完；节点上报只让候选继续，不直接设置源成员 merged。

身份与 Agent 终身一对一、invocation token 一次性规则不变。冻结节点使普通追加要求暂存；旧尝试回复不可推进新节点。私有权限不是 OS 沙箱，既有分支写守卫必须识别其窄授权，不能允许整合 Agent 操作 canonical 检出。

## 6. 验证与受检发布

1. 封闭成员并固定拓扑，生成最终 T；对子节点只跑专项及受影响回归，不逐层全量。
2. 在隔离检出固定最终候选，运行该项目规定的最终全量与必要集成验证；顶层交付负责人仍核对证据。父为开发 Worker 时，本次组合跑受影响集成，最终 main/owner 的完整组合负责全量。
3. 最终待发布单父提交 L 在验证前生成并固定，证据关联 L/T、测试代码、命令/范围、关键环境和工具版本。修改组合代码、成员或策略即作废；不能验证后再因时间戳重生成另一个 SHA，有依赖提交身份的测试须测精确 L。
4. 再读真实父 tip。不是 B 时，固定成员未变可先计算 `T′=merge3(tree(B), tree(B′), T)`，必要时在隔离区修复，形成新 generation/L′ 并重新跑最终验证；不能把旧 T 覆盖到新父上。成员或来源变化则从有效叶子重建。即使树未变，涉及 ancestry/ref 环境的检查也须重核，不只用树哈希复用所有证据。
5. 复核既定 L 的 `parent(L)=B`、`tree(L)=T`、成员均有效，持久化精确发布准备收据；真实写入前复核父/源 refs、generation、取消、权限、消息、检出与清洁度。
6. 源 ref 只验证不修改，父 ref 通过 CAS/ref transaction 与受检检出更新。发布后先核验精确 L 存活与现场一致，再在一个 DB 事务中结算完整成员、父 head 和来源事件。

验证执行器只运行项目明确授权、版本固定的验证定义，定义包含命令/argv、隔离工作目录、环境允许范围、超时、结果及日志引用；不能把某个来源报告中的命令字符串当作执行授权。未声明最终验证范围、授权变化或缺少运行环境时阻止发布并显示具体原因，不能将“无证据”标通过。复用受控命令能力须明确扩展到登记过的隔离检出，并保留未知副作用不重放规则；不是宿主机沙箱，也不开放任意路径执行。

最终验证期间持续流入的成果不会改变候选。目标被外部持续推进时不能承诺无等待，需显示“基线连续变化”，有界重试后等待真实安全点；不得强制 reset 或偷锁用户外部 Git。
