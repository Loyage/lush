# 通知与告知：知道变化，不替用户做决定

本章指导 Notice 的提醒设置、已读与消除交互。用户需要及时知道工作进展，但不应被重复告知打断，也不应因关闭一条提醒而误批准合并或丢失历史。接口与实际限制见[待决问题与告知](../reference/rpc/notices.md)，实现入口见[Web 模块地图](../engineering/modules-web.md)。

## 原则

- **待决与告知分开。** 待决问题需要明确答复；用户也可独立显式授权项目 [daemon 自动选择 Hook](../engineering/daemon-auto-select.md)，自动来源必须与用户答复区分。纯告知只表达已经发生的事实。「已知」不得答复问题、开启自动选择、批准合并、验收、重试或启动 Agent。
- **提醒与记录分开。** 关闭某类提醒只改变当前客户端的展示与系统通知，不阻止 runtime 留档、不改变未读记录，也不影响其它设备的偏好。
- **类别与渠道分开。** 用户可以只保留异常停止的页面告知条，仍接收工作收尾的系统通知。系统权限与总开关仍独立，不因页面偏好主动申请授权。
- **看见哪条，消除哪条。** 汇总条展示当前告知标题与剩余数量；「已知」仅标记当前一条，下一条仍可查看。已读是项目持久事实，在其它设备也生效。
- **手势只是快捷方式。** 手机横滑与「已知」按钮做同一件事；触摸、键盘与鼠标均有可见按钮入口，不能只靠用户猜手势。
- **事实来自来源事件。** 告知类别不能按标题或 Worker 的后来状态猜；未知来源保持可见，不因无法分类而静默丢弃。

## 取舍与边界

告知条保持精简，避免所有未读告知占满屏幕；完整记录在「待我处理」按需查询。查看 Worker 成功后可以自动已读，单纯「已知」无需导航。两种路径都必须在服务端成功后才移除告知；失败可重试，不伪装成功。

移动端横滑必须让位于垂直滚动、文本选择、短滑与取消手势；滑动后的合成点击不能误打开 Worker。刷新不得重复提交已读，也不得破坏正在操作的节点。动效遵循减少动态效果偏好。

系统通知只提醒新到事项，首次加载、刷新、切换项目与重新开启开关不得补发积压历史。窗口关闭后不提供后台推送；不为此引入全局调度或新实体。

## 反例

- 把「已知」连接到 notice.dismiss，让 Agent 把它当成用户拒绝或答复。
- 关闭提醒时删除历史，或批量标记尚未展示的告知已读。
- 依据「失败」这样的标题关键词判断类别，或用已重试 Worker 的当前状态给旧告知重新分类。
- 为待决问题也添加无须答复的滑动消除。
- 仅手机可滑动、没有按钮；纵向滚动误消除；写入失败仍把告知隐藏。

## 验收问题

- 关闭一类页面提醒后，它的历史、未读数及独立系统通知设置是否保留？
- 已知与横滑是否只处理当前一条、不导航、不调用 Agent，且服务端失败时仍可重试？
- 未决问题是否仍显示并需要用户明确答复？
- 触摸滚动、选择、取消与键盘操作是否安全？
- 重开浏览器后偏好是否按站点保留，不同 Host 是否隔离？
- 告知正文、来源与已读历史是否保留，来源分类是否不受 Worker 后续状态影响？
