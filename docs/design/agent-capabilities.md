# Agent 能力模块：短入口，按需指南

W217／D509 确认：参考 stablyai/orca 的薄 Skill 入口与当前 CLI 提供版本匹配指南的结构，将可选工作能力从常驻提示词拆出。用户在设备全局设置选择能力，不为每个项目重复配置。

## 必需核心与可选能力

模块包括进度汇报、子 Worker 委派、自动标题、上下文检索与结果告知。启用时提供简短的使用时机与加载要求；详细流程由对应 Skill 引导，通过 daemon 固定的 `lushw skills show ID` 按需读取。进度和自动标题有每轮触发要求，入口不能仅依靠模型自行猜测是否加载。

安全、权限、Git/worktree、消息交付、等待释放槽、既有后代的成果检查、实际调度与交付协议，以及最低测试责任始终属于核心。插件只教 Agent 如何使用已有能力，不提供另一套调度器，也不能改变权限或跨项目边界。

结果告知按 W326／D689 确认：任务只是分析，或用户明确要求做好后告知时，Agent 应主动发送包含实际结论的非阻塞告知，不能只留最终回答。它是默认开启、可关闭的内置 Skill，Pi 与 Codex 共用；与 runtime 状态告知独立，不为了减少重复修改用户 Hook，可能收到两条。告知不能代替决策、合并或验收，也不能把中途停顿冒充完成。

## 关闭与兼容

关闭只控制后续 invocation 的注入及主动使用，不撤销 CLI/RPC 权限，不中断当前调用，不取消已有 child，不改写历史。后续调用应收到关闭状态，避免旧会话残留指令导致主动使用；自定义 Prompt 和旧上下文不自动重写，这不是安全隔离承诺。

默认保持原已开启能力；进度继续兼容既有 `progress_reporting` 设置与历史读面。设备设置没有项目覆盖，不引入 Worker 级模块开关。Pi 的 Lush 模式与 Pi 默认模式均保留 Lush 必需核心并提供已启用内置 Skills；Codex 使用同一入口与 CLI 指南。manager、butler、explainer 不获开发插件。

## 验收问题

关闭的模块是否从后续调用的 Skill 列表和主动流程中消失？当前调用和已有 child 能否正常收尾？安全规则是否不依赖加载可选指南？模型是否能明确知道进度／标题何时必须加载？无项目、离线项目能否编辑设备开关？关闭是否被误称为权限隔离？第三方扩展与 Skills 是否仍保持显式配置、不被修改？

接口与开发分区见[工程契约](../engineering/agent-capabilities.md)。
