# Agent 的 CLI 能力发现与信息披露（提案）

本文细化[CLI 整体提案](cli.md)的信息披露层，面向使用 `lush_cli` 的 Valet、使用 `lushw` 的开发 Worker 及实现者。用户已确认按此方向改进方案；**仅为设计，help 搜索、工作流主题和机器目录尚未实现**。当前入口、真实身份与权限仍遵守[现行 CLI 契约](../reference/api.md)。

## 1. 目标：能找到、能正确调用、能正确理解结果

CLI 的主要消费者是 Agent，同时保留用户终端操作。不能只让命令名整齐：Agent 必须知道用户意图对应哪个能力、必要参数从哪里来、动作何时真正生效。采用“少量固定提示 → 分层 help → 按需工作流 → 可信执行反馈”，不把整份手册放进 Prompt，也不为每条命令新建模型工具。

| 披露层 | 默认内容 | 不放什么 |
| --- | --- | --- |
| 启动契约 | 真实身份／项目范围、固定工具、核心安全规则、短领域索引、目录版本与帮助入口 | 全部命令参数、项目历史、完整 schema、私有设置 |
| 根／组帮助 | 领域用途、直接动作／子组、适用场景、下一帮助路径 | 全树展开、长 RPC 表、每个动作重复一遍全局规则 |
| 叶命令帮助 | CLI 语法、条件、参数来源、作用域、效果、返回含义、示例与关联命令 | 要求模型自行推导的 RPC 字段映射、秘密或实时许可承诺 |
| 工作流帮助 | 少数跨命令主流程、步骤依赖、停止点和恢复边界 | 新执行引擎、可执行脚本、任意文件／用户扩展加载 |
| 执行反馈 | 可信效果证据、真实收据、下一合法动作与帮助路径 | 由错误字符串猜出的成功／未执行、自动重试建议 |

不要求每轮先读根帮助，也不要求每条命令执行前读 help。启动已提供足够索引、版本一致且用法明确时可直接调用；不确定参数、陌生能力或可信参数错误才按需查阅。核心安全约束仍必须注入，不能要求 Agent 先发现它们才能守住边界。

## 2. 一个 help 入口，多种有界读法

以下均是目标语法；`help` 后的 workflow 是文档主题，不是新的业务命令：

```text
lush help                                      当前视图的能力领域与少量主流程
lush help worker                               直接动作及子组，不递归展开所有叶
lush help worker merge request                 单条 CLI 完整用法
lush help --search '等待另一个工作合并'          搜索用途、名称和场景
lush help workflow                             可用工作流的短目录
lush help workflow conditional-input           一条完整流程
lush help worker merge request --json          同源的机器可读命令描述
lush help --all --limit 30                     当前视图全部命令的分页短目录
lushw help children spawn                      开发协作的叶命令契约
```

- 搜索只检索随代码发布的名称、用途、场景和少量中英文关键词，不检索用户数据、不调用模型或联网。结果明确是 command 或 workflow，附精确帮助路径；匹配不是自动选中或执行。
- 文本和 JSON 使用同一投影。默认文本紧凑、分节，适合模型阅读；JSON 用于严格校验、生成复杂配置和工具集成，不默认输出庞大的原始 schema。复杂 `--data` 的完整 schema 随叶帮助提供，类型不能只写成“object”。
- 根／组帮助只展开一层；搜索、workflow 目录及 `--all` 有界分页，支持 limit/cursor，明确 has_more 和续读方式。不以截掉后半段冒充完整帮助，也不让 Agent 每次扫全表。`--all` 只展开当前视图，不切换身份或披露私有材料。
- 单叶帮助一次提供完成调用所需的完整契约；公共类型可在同一输出解析引用，不能留下模型无法取得的 `$ref`。若单条契约过大，应简化接口或拆出明确可获取的命名子 schema，而不是隐式截断。
- 未知命令提供合法近似项和只读帮助路径，不自动纠错执行；旧路径只返回迁移提示。正文和 `--` 后的内容不能作为帮助选项误执行或误解释。

JSON 沿主方案的版本化外壳；`data` 必须含 `catalog_version`、`view`、`kind`（index/group/command/workflow/search）及对应描述，分页沿用 `page`。schema 描述的是**实际 CLI 位置参数、旗标、结构化负载及组合规则**，不是裸 RPC 参数；RPC 映射只供实现和高级诊断，Agent 不需要知道才能调用。

## 3. 不同 Agent 看见不同的静态视图

| 调用入口 | 默认发现范围 | 固定限制 |
| --- | --- | --- |
| 用户终端 `lush help` | 用户管理领域，必要时标注 invocation-only 的高级条目 | 看见说明不等于具备 Agent invocation |
| Valet 的 `lush_cli` | 通过静态审核的管理命令、管家自身事务与适用工作流 | 没有 Shell、任意 RPC、本地文件或私有材料；仍检查最新逐项权限 |
| 开发终端 `lushw help` | self、parent、children、question、skills | 数据操作绑定有效 invocation；不暗示项目枚举或跨亲缘权限 |
| Web Worker CLI 的帮助 | 可信用户上下文 lease 对应的已映射操作 | 不因使用 lushw 就获得 Agent-only 操作，不伪造 Worker token |

帮助视图由固定可执行入口、可信 bridge 或用户上下文通道传入；不让模型靠 `--role` 或伪造环境选择执行身份。静态视图生成不查询项目、不验证 token、不读取设备私有权限，因而可以离线；离线的 lushw help 也不证明当前有合法 invocation。

Valet 的默认目录不堆放本地认证、Host 进程操作等固有不可用能力；明确查询或搜索这些主题时，给出“需真实用户处理”的安全说明，不提供绕过路径。临时被权限配置禁用的**已审核能力**仍可以有静态说明，标明“实时许可未知”，而不是把当前禁用混成永久不存在。

Worker 能力开关只影响启动推荐与主动工作方式，不删除底层合法命令或既有 child 的收尾说明。Valet 不加载开发 Skills；其工作流是固定 CLI 文档，不是新的 Skill 执行／文件能力。用户终端的帮助阅读不扩大任何身份的权限。

## 4. 叶帮助必须回答的八件事

| 内容 | 示例要求 |
| --- | --- |
| 目的与非目标 | merge request 请求本轮合并，不开启持久自动合并、不直接证明代码落地 |
| 精确语法 | required、类型、枚举、默认值、范围、是否可重复、互斥／依赖及多种模式 |
| 参数来源 | 条件 revision 来自 worker merge show；不得与 automation show 的 revision 互换 |
| 身份与范围 | 用户／受控 Valet／开发 invocation 的适用性，目标类型、项目／设备及亲缘限制 |
| 前置读取 | 哪条查询得到目标、版本和状态；按模式列出实际前置读取，不凭摘要重建私有配置 |
| 效果与代价 | read/write、是否联网、是否可能调用 Agent、是否回收／删除资源、不可撤销部分 |
| 返回与恢复 | 已受理／等待／已生效／未知的区别，收据身份、合法下一步与必须停止的情况 |
| 示例与关联 | 最小主流程和一个关键易混场景；真实值须查询，示例 W5/REV 不是可直接执行的目标 |

以 `worker merge request` 为例，必须分别描述无条件 reserve 与带条件 merge_after 两条模式：后者需要条件 revision，前者不强制多读一次私有／无关状态。所需 RPC 和授权也按模式表达，不能把整个命令标成“允许”就放行全部分支。

以 `children spawn` 为例，说明目标写法、真实父绑定、派工会创建独立 Worker、正常派出后结束本轮，以及 child 交付后如何检查；不诱导 Agent 轮询等待，也不把暂时关闭委派推荐解释为既有 child 消失。

## 5. 工作流提供组合知识，不提供额外权限

首批只保留现有关键主流程，不为每个参数组合扩建指南：

- `conditional-input`：区分新建／追加 → 核验真实目标及依赖 → 提交 order 或保存并提交 draft → 解释挂载收据并结束。用户说“合并后”不擅自替换为“本轮已结束”。
- `register-and-attach`：读取对应 revision → 注册定义 → 确认注册完成及固定版本 → 独立挂载 → 报告真实收据。注册失败、待确认或未知时不得继续挂载。
- `review-and-accept`：读取成果与真实交付事实 → 必要预检 → 合法验收 → 核对回收结果；child 默认保留、权限与质量判断不能由流程自动代替。
- `delegate-and-report`：仅 Worker 视图，说明派工范围／测试责任、结束调用、后续成果检查与最终报告；不把验收回收设为收到成果后的默认步骤。
- `ask-user`：区分决策问题与 info；Worker 本地准备问卷后发布，Valet 使用内联结构化问卷；发布决策后结束本轮，不自答或执行尚待选择的动作。

同一 workflow 可按可信视图生成不同步骤；不适用的流程不出现在默认目录。每一步引用稳定 command ID 和模式名，参数／schema 从命令声明源生成，不手工复制第二套命令拼写。流程只组织既有规则；安全和权限边界仍在原契约维护，不借此改调度或重放历史。

## 6. 静态缓存与动态事实分开

`catalog_version` 覆盖路径、参数 schema、行为说明、工作流及身份投影规则；`version` 表示机器输出协议格式。启动信息携带固定 CLI 的目录版本，同版本已读帮助可以复用。版本变化、可信协议不匹配或命令迁移提示只使相关知识失效，不重发刚才的写操作。

帮助中只说明静态 applicability，不能输出虚构的 `allowed:true` 或固定的实时 automatic/confirmation 结论。设备最新权限、本轮用户授权、当前目标状态、冻结与 revision 在执行时检查；无需每次先拉取全量权限。遇到明确授权不足时用已有安全入口核对或问用户，不自行提权；权限查询也不保证下一刻准入。

准备将发生的动作时，Agent 读取所需的真实目标和 revision；缓存的示例、旧状态和旧批准不能代替。目录与后台版本不匹配时提供安全诊断，不能用“help 看得到”证明当前运行进程支持该动作，也不自动更新／重启服务。

## 7. 执行反馈也是披露协议

工具返回值保持结构化。Valet 的 bridge 保留 transport／exit_code 与实际命令结果的区别；原生 CLI 的 `--json` 不混入人类提示。沿主方案的 outcome 和既有可信诊断表达效果，必须保留 receipt、coverage、截断事实以及合法的下一帮助路径。

| 可信结果 | Agent 应做什么 |
| --- | --- |
| 参数不合法且明确 not_started | 查对应叶帮助，修正参数；这不授权改换身份或扩大目标 |
| 权限／用户范围不足 | 停止相关动作，说明需要的用户决定；不能换等价命令绕过 |
| 陈旧 revision／当前状态阻塞 | 重新读取必要事实，重新判断原意图是否仍有效；不循环重发写入 |
| pending_confirmation／waiting | 报告已提交并结束本轮，由 runtime 推进；不轮询或自批准 |
| 方法效果已证明 applied | 只报告该方法完成，不将注册当挂载、合并请求当合入、取消请求当进程退出 |
| unknown／缺少完成证明 | 保留未知；仅按已有收据核对路径进行必要读取，不更换去重身份重放 |

建议执行反馈里的 next/help 使用 code-owned 的 command ID／帮助路径，不复制用户正文或自动拼出带秘密的可执行命令。缺少可信证据时必须保守为 unknown，不能仅凭退出码、异常文本或下次读取到的近似状态补造完成证明。

## 8. 实施接线与验证标准

在现有 `src/cli/catalog.js`、CLI 参数契约及 parser 上演进 CommandSpec；增加用途、模式、参数来源／依赖、效果、输出与恢复说明、检索关键词，避免维护一份平行 Agent 专用 API。固定 workflow 描述只引用 CommandSpec；文本／JSON help、启动短索引、Web 学习页、静态准入和用户上下文映射复用这些定义，dispatcher 仍独立核验真正授权。

同步更新 `src/agent/prompts.js`、随代码 Skills、`src/agent/management-cli.js` 和共享协议的使用说明；管理模型工具仍只有 `lush_cli`，不恢复 manager_catalog 等独立工具。bridge 当前会为普通命令加入 JSON 输出选项，改造时必须区分**工具外壳 JSON**和**help 正文格式**：默认 help 返回紧凑文本，只有显式请求机器目录才返回 schema，不能因隐式旗标把每次帮助膨胀成完整机器表。

先验证三条现有真实链路：用户离线 help → 实际命令；可控 Provider 的 lush_cli → 分层 help／工作流 → 权限核验 → 执行与返回；Worker invocation 的 lushw → 亲缘核验 → 问卷／派工与非阻塞返回。Web 用户上下文复核其静态映射与真实 lease，不能用模型自述身份替代。

优先改已有 CLI／管理 bridge／Worker 上下文主流程，复用主方案的专项与集成组合。验收须证明：索引可达所有保留能力；搜索只查固定文档；帮助不发现项目或读秘密；文本与 JSON 和实际 parser 同源；版本变化可识别；当前未授权动作执行仍拒绝；工作流前置值来自真实查询；等待与未知不会被当作成功或自动重试。真实模型的发现成功率、调用次数与 token 开销可后续另做小规模评估，静态／可控 Provider 测试不冒充模型理解效果已验证。
