# 历史输入与草稿：原话可追溯，暂缓可调度

本章面向修改输入框、暂存与历史检索的开发者。用户需要低成本保留突发想法、反复修改，并在合适的时候明确交给 Lush；也需要找回曾经发出的原始命令。操作说明见[历史输入与暂存](../input-history.md)，接口边界见[核心 API 收敛](../engineering/core-api.md)。

## 原则

- **记录不等于执行。** 暂存只保存项目内的正文、引用和父 Worker 身份，不创建工作区，不调用 Agent，不自动排队。关闭浏览器后仍能找回。
- **一条想法，一次明确授权。** 发射是可靠挂载需求，不保证立即创建 Worker。条件信号、父空闲与安全准入由 runtime 承担；新建实际成功后才产生原始 Input，普通追加只产生消息收据，不伪造 O 编号；手动创建的空 Worker 首条输入绑定真实 Input/O，创建本身不授权执行，见[手动创建](../reference/rpc/tasks.md#手动创建与首条输入w337d698)。完整契约见[条件发射](../engineering/conditional-emission.md)。
- **先接住人的需求，内部等待由软件承担。** Worker 冻结只限制 Agent 执行与 Git 写入，不应让用户无法表达。合法追加输入须先可靠保存，由 Worker 代管，等待当前交付收口、整体解冻与 Agent 实际退出后再投递；不能把「已保存」说成「Agent 已收到」。暂存输入不得打断固定提交的修复，也不得被自动验收、归档吞掉。
- **原话与后续工作分开。** 暂存可编辑、删除；已发出的原始输入不可改写。后续要求走 Worker 追加消息，而不是把历史原话改成新的指令。
- **历史必须可查全。** 搜索针对项目全库历史输入正文，不局限于首页快照或已经加载的记录；三种模式的来源范围见下文。旧流程输入、关联 Worker 已不存在的输入也不能无声消失；缺失状态明确显示未知。例外只有用户经资源预检和最终确认执行 Worker 彻底删除：无剩余使用者的原始输入与已发射草稿随所选子树一起清除，不把此操作冒充普通归档或历史筛选。
- **归属不能随浏览器或 Git 切换漂移。** 暂存时保存父 Worker 身份，发射前可显式更改；代码基线在实际创建时固定，不在保存想法时锁死。父Worker失效要保留草稿、提示重选，不能静默改投 main 或当前分支。

手动创建遵守 A337-1／D704：项目级入口与 Worker 内操作分开。Worker 内只有「创建子 Worker」，默认空白；复制默认取当前 Worker，也可选择其已有直接子 Worker，实际父级固定当前 Worker。来源不是任意项目检索，子项按需分页，创建本身不授权执行；后续首条输入才绑定原始 Input 并启动，手动创建不套用 Agent 委派的自动合并授权。

## 状态是事实的投影

暂存不属于 Worker 生命周期。发射先展示等待条件、排队准入、正在投递或未知结果等持久事实；实际创建后才展示对应 Worker 的状态。多个条件全部满足且核验本轮成果，不能把调用返回或旧轮合并误作完成。静息等待和持续独占分开表达，独占不是自动合并授权。

合并是另一个维度。「待验收」和「已合并」可以同时成立；「已完成」也可能没有代码合并。不要把Worker生命周期、代码交付与归档压成一个互斥状态，不为历史页再维护一套可漂移的Worker状态机。追加开发后不得把上一轮落地当成本轮已经交付。

W306／D670：历史输入与草稿是两个独立页面，不再用同一列表的 Worker 状态筛选区分。历史输入帮助用户查找自己在什么时候对项目作出了什么批示，按发送时间倒序检索原始 Input、来源可证明的用户追加 Message，以及主输入框提交的管理需求；三种模式默认全选，默认突出原文、类型与时间，Worker／合并状态筛选按需展开。消息与管理需求保留独立来源，不伪装成 Input、不造 O 编号；定时信号和系统消息不收录，旧缺少可信用户来源的消息保留在 Worker 中，不猜测归类。原文详情只读并可定位来源，Worker 状态不证明单条消息已处理。

草稿页聚焦尚未发送的需求及其执行条件，分「工作暂存」「追加输入暂存」「管理暂存」，列表常显去向、条件摘要与等待／异常状态。未授权或已撤销的草稿可编辑；等待条件、等待安全准入、投递失败与结果未知仍归草稿，并只读显示授权事实及合法撤销入口。只有实际创建 Input 或追加 Message 已可靠入箱后才进入历史，不以点击提交或挂载 ACK 当作已发送，也不以 Agent 是否已阅读为归档标准；成功后列表不重复显示源草稿，历史保留明确来源草稿的条件／独占收据入口。管理指令提交成功即有其真实管理记录。页面拆分只是读面归类，不删除、迁移或改写既有记录，不新增调度引擎或放宽管家权限。

两个页面均在全库分页之前完成各自范围筛选；非文本筛选即时生效但不应用未提交关键词，同页详情往返保留筛选、分页与阅读位置。草稿分类切换也须使旧查询与分页失效，不能让工作暂存的迟到响应覆盖追加暂存。

Worker 对话中的「输入指令」按可信提交来源显示作者：仅明确的用户输入显示当前软件登录账号名（不是模型来源账号），头像使用用户名第一个 Unicode 字符簇；管家或开发 Worker 提交的目标／挂载追加显示其真实编号与机器人头像，系统输入明确标为系统。旧记录缺少可靠来源时显示「来源未知」，不因它是原始目标、来自空 sender 或带旧追加编号就冒充用户；普通系统／Worker 通信仍独立归类。账号通过根 Host 会话接口一次读取，只留当前 UI 会话内存；加载失败或无账号明确显示名称未知，不编造姓名，不将名称作为 HTML。原始目标只按真实 `task.input_id` 显示 `O<Input ID>`，没有 Input 不造 O；明确用户追加输入只显示持久 `append_number`（如 `A198-1`），来自 Event 或关联 Message。历史缺号回退消息 `#ID`（消息身份也缺失则标未知），不从事件、分页或显示顺序猜编号。渐进读取名称／编号不得覆盖别页或丢失当前阅读状态。

## 交互与失败保护

- 产品命名按模式、内容、状态分层：模式为「新建工作／追加输入／管理 Lush」，内容为「工作指令／追加指令／管理指令」，动作统一「暂存／提交」。提交表示执行授权，不保证立即执行；内部发射协议、实体、API 与历史身份不更名。编辑时模式与去向常驻，placeholder 只提示正文；输入入口与执行授权分开，打开面板不调用 Agent。具体文案与现有能力边界维护在[用户操作](../input-history.md)。
- 主输入与草稿详情统一：Enter／Shift+Enter 换行，Ctrl/⌘+S 保存草稿，Ctrl/⌘+Enter（含 Shift 组合）提交；新建草稿与续写更新共用保存路径，不授权执行，触屏保留可见按钮。所有页面默认新建，默认父 main；明确点击「追加输入」才切换到指定目标，隐藏父选择但保留暂存能力。条件配置只在草稿详情提供，主输入可继续已有条件草稿并按原条件授权；D758：草稿详情与条件自动化嵌入编辑器默认展示执行条件摘要、自然语言条件输入和管家挂载入口；手动条件、独占与运行参数等高级项按需展开。W395／D773：执行条件、运行设置、引用同级对齐，运行设置与引用分别展开；运行设置展开即编辑，不再二次进入弹窗。展开不冻结默认，修改有效值成为本条选择，自定义 Prompt 仍在授权前确认风险。收起保留设置，已有条件须以简要标注和「按条件提交」明确提示。引用附件不支持时拒绝而保留原文，不静默丢附件。
- D758：输入入口只显示三种模式及各自草稿数，不铺开草稿正文或逐条恢复操作；先进入编辑器，再通过常显的选择草稿入口按模式浏览并明确恢复原目标。计数覆盖本项目该模式未发送草稿及去重后的本地编辑，未读完或读取失败不得冒充零。等待授权、结果未知等记录只查看收据，不重作普通可编辑草稿。
- 自然语言条件发送先保存草稿，再创建普通管家处理指定草稿版本的条件设置与发射挂载；输入或保存条件文字本身不授权调用。管家创建与挂载成功分开呈现，复用既有条件、自动化与权限；目标／版本变化、语义不明或现有能力无法表达时须询问或拒绝，不猜测、不静默立即发射，也不扩大管理草稿自身的条件能力。
- D753／D754：同一个编辑器、同一份编辑状态，底部便携入口与正式详情只是宿主。位置切换不复制正文、引用、去向、条件、独占、profile、revision、正文历史、请求锁或去重身份，同草稿不能有两个活跃提交器。底部只常显正文、去向摘要、保存状态、基础工具和主要动作；可编辑目标、条件、运行设置与引用完整信息在详情；W395／D773 将删除直接放在详情操作行，保留危险色和确认，不再藏入独立折叠。详细编辑与到底部继续编辑双向保留原条目和阅读上下文；独立写新的一条保留原草稿。
- 保存首次创建、之后更新同一草稿，两处均保留内容、不执行。离开整条编辑（互切、收起、换条目／去向、站内导航）自动保存，与提交共用串行队列；编辑器内失焦或展开设置不算离开。保存失败阻止本次站内离开；冲突保留本地、展示服务器最新版，再显式整理，不要求先复制，不静默重试覆盖。浏览器关闭／崩溃不承诺异步保存，以项目隔离的浏览器恢复兜底。黄点仍表示有未完成输入，不表示保存失败。
- 管理也是第三类项目草稿，支持新建与追加原 V，忙碌允许保存而提交仍须空闲可用。管理不支持条件、独占或附件，profile 仅新建可选。权限选择只在详情本次明确提交时核对完整定义并重新验密，不入草稿／浏览器快照；恢复和下一条默认普通，unknown 只能查精确原收据，不改走普通入口补发。详见[管理提权契约](../engineering/administrator-valet.md)。
- 主动继续项目暂存应是同项目、同模式与同目标的完整草稿续写（包含管理），不是复制正文。检索必须查完全部分页；恢复身份、版本、引用与条件，再次保存更新原草稿，授权走精确保存版本。切换保留本地编辑，已授权等待、结果未知及已发送记录不得重作普通草稿；去向、版本或状态变化必须显式核验，不能静默覆盖或直接发送。具体操作见[用户操作](../input-history.md#就地继续草稿)。
- 挂载 ACK 后留在原页，不打开不存在的 Worker。草稿详情保持只读收据，直到实际获得 Input／Message 才可转到历史原文；独占意愿必须仍可定位与释放。普通追加不转成 O 原文；空 Worker 首条输入按真实 Input 收据定位 O。保存比较正文、去向、引用、条件和独占；运行参数仅发射时写入。Ctrl/⌘+S、撤销／重做与按钮共用编辑、版本和单飞保护，普通 Enter 换行，Ctrl/⌘+Enter（含 Shift 组合）先保存修改再提交草稿。
- 「管理 Lush」是显式的第三种去向，不是开发 Agent 换一个 Prompt。其独立提示词、无 Git 目录和可信工具不加载开发上下文；普通 Agent 不扩权。管理权限分级，危险请求精确预检后由真实用户确认；能力发现不能冒充执行授权。详见[管理型 Worker](../engineering/hook-signals-management.md)。
- 提供可见按钮，不要求触屏用户记快捷键。两处均常显基础撤销／重做与引用数量，文字历史在位置互切及保存后保留，不回退附件、设置、服务器版本或已发请求；成功消费才释放，失败和在途新编辑保留。手机按可视区域避让软键盘，按钮换行、不挤成小字。执行授权必须带 Agent 调用代价标识，参见[按钮帮助](ui-guidance.md)。
- 重复按键与点击不能创建多个 Worker。多标签编辑必须检测版本冲突，不以最后一次请求偷偷覆盖前一次保存。
- 请求失败保留原文与引用；请求在途时新打的字、新加的引用不得被旧请求的成功回调清掉。服务端确认成功后立即释放本条输入，不把列表刷新或详情加载算进提交锁；后台更新失败不冒充提交失败，也不诱导重复提交。
- 页面切换、搜索或刷新使旧响应失效，旧响应不能把用户拉回旧页面。后台读状态不覆盖正在编辑的想法。
- 引用是附件，不混入正文；保存快照与来源定位沿用[上下文引用](references.md)边界。

## 取舍与反例

完整历史可能很长，因此服务端检索、分页返回预览，按需读取原文。分页不是删历史，预览截断必须可见。显式刷新优先于频繁重画编辑中的页面。

以下做法违背目标：

- 暂存时就创建 Worker 或调用 Agent，把想法库变成不受控队列。
- 恢复旧批量 planner 提交流程，让一条暂存绕过当前指令协议。
- 只搜索首页最近Worker，却宣称能查全部历史。
- 将尚未发送的想法、等待条件或结果未知的授权混入历史，或因页面拆分删除草稿收据。
- 把条件和管家调度能力默认藏到多层菜单，或将草稿列表变成横向溢出的复杂表格。
- 父 Worker 不可用时自动选择另一个归属。
- 把「已合并」当作验收完成，或悄悄改写已发出的原话。

## 验收问题

1. 用户能否只记录、不执行，并在重开页面后继续编辑？
2. 全部原始输入是否可搜索，未知关联是否如实保留？
3. 暂存发射是否沿用当前指令的安全、身份与 Git 准入？
4. 重复提交、多标签冲突、失败与迟到响应是否保住用户文字？
5. 状态是否允许「已合并但待验收」，且不误报后续轮次？
