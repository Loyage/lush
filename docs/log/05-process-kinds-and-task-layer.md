- [x] PID 0 创建权限收窄为只能创建 `project-manager`：`templates/lush-root.json` 的 `child_templates` 从 `["*"]` 改为 `["project-manager"]`（只改这一处模板文件）；新增 `Repository.replaceSnapshot(pid, snapshot)`（「整份替换」的兄弟：逐字段 `jsonDump` 比较，完全相同或进程不存在返回 `[]`，有差异才在同一事务里 `UPDATE processes` 并记 `template_refreshed` 事件，`data.fields` 按稳定顺序列出值变了的键与被移除的键）与 `ProcessManager.refreshRootTemplate()`（可区分「没变化 / 变了哪些字段 / 模板缺失」），daemon 启动在 `ensureRoot()` 之后、开始服务之前调用它（`changed` 打 info、`missing` 打 warn，其余启动顺序不变）；文档写明 PID 0 是「快照是创建时的完整副本」的唯一例外（daemon 每次启动从当前加载的 `lush-root` 刷新，区别于 `template_backfilled` 的「只补缺失字段」），且它只能创建 `project-manager`（用户模板也不在其列，`child_templates` 是显式列表）。测试：`test/helpers.js` 新增 `permissiveRoot(manager)`（明确放宽测试根、不新建进程），core / runtime / agent / pi / rpc / openai 里把 PID 0 当「什么都能建」的地方改用它，core 新增正面用例（白名单与 available_child_templates、刷新语义与幂等、模板缺失）；`test/cli.test.js` 的父子链路全部改走 PID 0 → `project-manager`(1) → `project` / `generic-task` / `research-task` / `generic-service` → `dev-task`，PID 期望随之更新，并补一条 e2e 断言 `process spawn 0 generic-task` 被拒（退出码非 0、stderr 含 `cannot create template generic-task`）而 `spawn 0 project-manager` 成功；`examples/mvp_demo.js`、Justfile `bootstrap` 与 README 示例同步，`just verify` 测试数更新为 132。132 项测试通过（`bun test`）、`bun run demo` 通过。
- [x] 模板按层级顺序排列（不再按文件名字母序）：`src/template_loader.js` 新增 `hierarchyLevels()` / `orderByHierarchy()`，loader 在加载完全部模板并校验 `child_templates` 引用之后重排 `templates`——层级 = 从「没有其他模板能创建它」的模板出发的最长路径（`*` 与自引用不算边，环在递归走到的那条边上截断以保证终止），同级按名称排序，因此顺序与文件名无关；`ContextBuilder` 的 `available_child_templates` 直接吃这个顺序，于是呈现根在前的拓扑序（`lush-root` → `project-manager` → `project` → `dev-task` / `research-task` → 它们声明的 `generic-service` / `generic-task`），模板 JSON 一行未改（模板字段契约不变，没有新增 `order` 之类的键）。测试：core 新增用例断言完整加载顺序、断言「没有任何显式父模板排在自己的子模板之后」这条不变量，以及一个 project 实例拿到的 `available_child_templates` 就是同一顺序；同步 architecture / process-model / README 的模板段落与 `just verify` 测试数。134 项测试通过（`bun test`）。

- [x] `project` 不再能创建 `project`（开 / 关项目是 `project-manager` 的职责）：`templates/project.json` 的 `child_templates` 去掉 `"project"`，只留 task 类子模板（`dev-task` / `generic-task` / `research-task` / `generic-service`），其它字段、其它模板一行未改。嵌套 project 现在在创建时被白名单拒绝——`process.spawn` 先查父进程创建时快照的 `child_templates`，命中即报 -32010 `process <pid> cannot create template project`（与 PID 0 只能建 `project-manager` 同一条路径），因此 `ContextBuilder` 注入的 `available_child_templates` 里也不会出现 `project`。测试：core 新增 1 条用例（project 建 project 被拒且消息含 `cannot create template project`、模板白名单精确等于四个 task 类模板、`project-manager` → `project` 仍然成功、project 实例拿到的 `available_child_templates` 不含 `project` 但含 `dev-task`）；core 的层级顺序用例与 `test/runtime.test.js` 里「project 用 `process_spawn` 建 project 验证必填 `path`」这条原意不变的断言改走合法链路（前者期望列表去掉 `project`，后者把那次 spawn 交给 `project-manager` 的 AgentTools，并补一条断言 project 自己 spawn 被工具报错），没有放宽实现；同步 process-model（`project` 模板段落）/ README（project 段落、`just verify` 测试数）。`project` 的 `system_prompt` 里那句把 `project` 列为可建子模板的广告也一并去掉（改为「开 / 关项目由 project-manager 负责，你不能再建 project」），并加一条断言防止再写回去。既有 `project` 进程的白名单是创建时快照，改模板不追溯：本机 PID 3 / PID 8 用 `Repository.replaceSnapshot` 把 `child_templates` 对齐当前模板（只动权限字段，各记一条 `template_refreshed`）；这与 PID 0 的启动刷新不同，是一次性对齐，新建实例要重启对应 daemon 才拿到新白名单。135 项测试通过（`bun test`）、`bun run demo` 通过。
- [x] 模板文件按 spawn 树分层摆放（每个模板 `<name>.json` 同级一个同名文件夹 `<name>/`，里面是它能直接创建的模板），`child_templates` 改写成相对自己文件的路径：`templates/` 从平铺变为 `lush-root.json` + `lush-root/project-manager.json` + `lush-root/project-manager/{project.json,generic-task.json,generic-service.json,research-task.json}` + `lush-root/project-manager/project/dev-task.json`（共享模板 `generic-*` / `research-task` 跟最浅的父模板 `project-manager` 放一起，目录名不带序号），`child_templates` 相应写成 `lush-root/project-manager.json`、`project-manager/project.json`、`project/dev-task.json`、同目录的 `generic-task.json` 与自引用 `research-task.json` 这类相对路径。`src/template_loader.js`：新增 `templateFiles()` 递归收集 `**/*.json`（每个目录内按名称排序，保证错误可复现），新增 `resolveChild(entry, templateName, file)`——`*` 原样保留；含 `/` 或以 `.json` 结尾的条目按「相对声明文件所在目录」解析（先 `path.resolve` 再查 `files: 绝对路径 → 模板名`，查不到就报 `unknown child template <entry> in <name>: no template file at <path>`）；不以路径形式出现的条目仍按模板名解析（程序化 `register` 没有文件可相对，含自我引用），所以白名单、快照、`available_child_templates` 与权限比对里始终只有模板名，本次改动对既有进程的 `child_templates` 快照零漂移（`refreshRootTemplate` 不会因此记事件）。`register(value, { file, resolve })` 新增文件来源与「先注册全部文件、再解析路径」的两段式加载（相对路径可以指向后面才注册的文件正是树形布局的要点），`origins` / `files` 两张表记录模板与文件的对应关系。`src/identity.js`：fingerprint 的模板面改为递归（`surfaceFiles()`，目录内按名称排序），嵌套子目录里的模板同样算「喂给 agent 的提示词面」。测试：core 新增 1 条用例（子目录递归加载、`sub/mid.json` / `../shared.json` / 同级 `leaf.json` 三种相对写法都解析成模板名、路径指不到文件时报错、无文件的 `register` 写路径报错且不入表、裸名字与自引用仍可用），层级顺序用例补上三个 `origins` 断言钉住 `lush-root.json` / `lush-root/project-manager.json` / `lush-root/project-manager/project/dev-task.json` 这个摆放。文档：architecture / process-model / rpc / README / AGENTS 的 `templates/*.json` 全改成 `templates/**/*.json` 并说明目录即 spawn 树、`child_templates` 的相对路径会被解析成名字。136 项测试通过（`bun test`）、`bun run demo` 通过。

- [x] `dev-task` 新增子模板 `worktree-service`（`templates/lush-root/project-manager/project/dev-task/worktree-service.json`，`dev-task.child_templates` 从 `[]` 改为 `["dev-task/worktree-service.json"]`）：description 就是「给当前项目开的 git worktree 的管理器」，type=service、singleton=false、`child_templates: []`，只声明一个变量——保留名 `path`（必填、不可变、已存在的绝对目录），于是 Core 的 `checkWorkdir` 在创建时就拒绝缺失 / 相对 / 不存在的地址（-32602），而同一个变量又使它成为该 service 的 agent 工作目录（`src/agent/invocation.js` 读 `state.params.path`）：worktree 地址就这样绑在它身上，它一被 call 就站在那个 worktree 里。`dev-task` 的 `spawn_prompt` / `system_prompt` 同步改写，去掉「dev-task 不创建子进程、自己干到底」的说法，换成协议：先向父进程拿仓库 `path` 与 `branch`，`git -C <仓库> worktree add <目录> -b <分支>`（目录默认取仓库同级的 `<仓库名>-<name>`，先 `git worktree list` 跟随仓库既有约定，不建在仓库内部），确认目录存在，再 `process_spawn` 出 `worktree-service` 并把 `variables.path` 绑上，实际改动 / 自测交给它（一次只说一件事、不并发 call 同一个进程），自己不写业务代码、不 merge / rebase / 删 worktree。`worktree-service` 的 `system_prompt` 让它每次 call 先认清自己在管什么（`git rev-parse --show-toplevel` / `--abbrev-ref HEAD` / `git worktree list`，写进 state）、把改动限制在这一个 worktree 内、git 只做增量（`commit` 可以，push / rebase / `reset --hard` / 删分支 / `git worktree remove` 要先说清再等指令）、不建子进程、不 `complete`（Service 不自行结束）。它位于第 4 层（`dev-task/` 子目录里），所以 `available_child_templates` 里它排在 `generic-service` / `generic-task` 之后；`dev-task` 不再是叶子。测试：core 新增 1 条用例（类型 / 单例 / 唯一声明与不可变性、`project` 建它被拒 -32010、缺 `path` / 相对 `path` / 不存在 `path` / 未声明变量都 -32602、`update_vars` 改不动它、它自己建子进程被拒），dev-task 用例的白名单断言改为 `['worktree-service']`，层级顺序用例把 `worktree-service` 排进期望顺序并补一条 `origins` 断言；`test/pi.test.js` 原有的「`path` 就是 agent cwd」用例扩到新模板（dev-task → worktree-service 的 cwd 与 `--name` 都由 worktree 与短名决定），不需要新 fixture。文档：process-model 新增 `worktree-service` 段落并更新 `dev-task` 段落与模板摆放、architecture 的目录例子、README 的模板段落与 `just verify` 测试数。既有 `dev-task` 实例的白名单是创建时快照，改模板不追溯——新建实例要重启对应 daemon 后才拿得到新白名单。137 项测试通过（`bun test`）。

- [x] 统一进程类型：所有进程都是 service，删除 task / service 之分。模板 `dev-task` / `research-task` / `generic-task` 的 `type` 从 `task` 改为 `service`（其余模板本来就是 service），`TemplateLoader` 只接受 `service`（其他值在加载时报错并说明原因）。Core 收敛成一套状态机（`src/core/lifecycle.js`）：created → running / stopped / failed，running → stopped / completed / failed，stopped / failed → running / reclaimed，completed → reclaimed；`cancelled` 随类型之分一起移除（停止统一是 `stopped`，kill 与 stop 同义、对已结束节点幂等），`TASK_TERMINAL` 换成 `FINISHED`，`ProcessManager` 的 `stop` / `kill` / `complete` / `reclaim` / `orphanEvict` / `repository.transition` 的级联冻结 / `removal.js` 的 purge 全部去掉类型分支（任何进程都能 start / stop / kill / complete / reclaim，`complete` 仍要求 running，`reclaim` 仍只接受已结束的进程）。Persistence 保留 `processes.type` 列但恒写 `service`（唯一值 CHECK），状态 CHECK 变成与类型无关的六态；`PRAGMA user_version` 升到 2，`Database.migrateV2()` 把 v1 库原地重建（SQLite 不能删 CHECK：建新表 → `SELECT` 时把 `type` 写成 `service`、`cancelled` 折成 `stopped` → drop → rename → 重建索引，切换期间 `foreign_keys = OFF`），既有 `.lush` 无需手工重建。提示词同步：`guide.js` 的 COMMON 改成「只有一种节点（type = service）」，`process_complete` 的工具说明与 CLI 说明改成「任何进程都能 complete，长期服务默认不该自己调用」；`dev-task` / `worktree-service` / `generic-task` / `project` / `project-manager` 的 spawn / system prompt 里与类型绑定的措辞改写（worktree-service 仍是「长期服务，不自行结束」，但不再以 task / service 区分）；CLI 声明树（start / stop / kill / reclaim / complete / delete / purge / orphans / list / session）与 `docs/process-model.md` / `docs/rpc.md` / `docs/architecture.md` / `README.md` 的生命周期、孤儿回收、模板 `type` 字段说明同步更新。测试：core 新增「v1 库迁移」用例（含 `foreign_key_check`、contexts 存活、旧 CHECK 不允许的 service → completed 现在可用、cancelled → stopped），模板校验补一条 `type: "task"` 被拒，原有断言的 `type: 'task'` / `to: 'cancelled'` / 文本里的 `task` 改为 `service` 与 `stopped`，「task 不能 complete / service 不能 stop」那组反例改成状态机反例（reclaim running 仍被拒）。142 项测试通过（`bun test`），mock provider 的 `bun examples/mvp_demo.js` 通过。

- [x] 引入 task 层：Process 变成被动节点，Task 成为唯一会运行 agent 的工作单元，并可向下游派子 task（task 树）。`processes` 去掉 `type` 列、状态收敛为 created / active / stopped；新增 `tasks` 表（pid、parent_task_id、root_task_id、goal、status、result、error、state、时间戳）与 `task_events`，`agent_calls` / `messages` 增加 `task_id`（`user_version` 升到 3，`Database.migrateV3()` 重建 processes 并把每条历史 call 变成一个根 task、其 messages 一并挂上，v1 库按 v1→v2→v3 链式迁移）。Core 新增 `src/core/tasks.js`（派活规则：只向直接子 process、一个 process 一个活动 task、只能等自己树里的 task；`task_wait` 的等待用内存 waiter 并在终态唤醒；complete 要求子 task 已结束，fail / cancel 级联整棵子树——「终态 task 没有活动子 task」的不变量；task 树 / 列表 / inspect 读模型），`lifecycle.js` 拆成两套状态机，`ProcessManager` 变成 process + task 双面门面（`call` 建根 task 并阻塞、`task*` 一族、stop 拒绝有活动 task 的节点、orphanEvict 先取消 task），`removal.js` 让 delete / purge 连带删除（并先取消）节点上的 task。Runtime 改为 task 驱动：`startTask` 打开一个 task 的 run、每 task 一次 invocation、`waiting` 状态与「agent 先回答、子 task 结束后带结果唤醒」的续跑（上限 `LUSH_TASK_CALLS`，默认 12），agent 空间 id 改为 `TASK.N`，pi session 按 task 命名（`lush-task-<id>`），环境变量新增 `LUSH_TASK_ID`。Agent 工具换成 `task_self` / `task_children` / `task_spawn` / `task_wait` / `task_cancel` / `task_complete` / `task_update_state` + `process_*`；`guide.js` 重写为「被动 process + task 树」；模板去掉 `type` 字段（七项契约）并按 task 模型重写全部提示词。CLI 顶层新增 `call`（在节点上开 task 并等待，`--detach` / `--interactive` / `--dry-run`）与 `task` 命令组（list / tree / inspect / result / wait / spawn / cancel / complete / delete / history / session / attach / update-state / agents），`process` 组只留被动节点操作（list / tree / inspect / children / spawn / start / stop / delete / purge / update-state / update-vars / orphans），RPC 方法面同步（`call.*` / `task.*` / `process.*`），Justfile 与 README / process-model / rpc / architecture 文档重写。测试 146 项通过（`bun test`），`bun examples/mvp_demo.js` 重写并通过。
