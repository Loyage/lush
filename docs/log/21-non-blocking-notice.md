# 21 · notice 不阻塞：答复从「工具返回值」变成「下一次输入」，task 多一个 awaiting

> 目标：把 notice 从**阻塞型等待**改成**挂靠型上报**——agent 上报一条 notice 时，把自己（也就是那个 task 的收件箱）一并挂在这条 notice 上；用户 `answer` / `dismiss` 后，答复会自然地走回那个 task，agent 在**下一次 invocation** 接到它，再接着干活。
>
> 上一轮的形状（[09](./09-agent-notices.md) / [10](./10-worktree-merge-gate.md)）是「阻塞」：`notice` 工具停在 `waitForNotice` 上、`notice.post` 的 RPC 一直挂着、`lush notice post` 的进程不返回，上报的 task 停在 `waiting`。这条通路和 [11](./11-task-inbox.md) 建立的「阻塞移到 task 层」是两套语义：一个 agent 因为等人而不是因为等下游，**在工具里**停住了一次 invocation，而 `waitForTaskInput` 那套 `waiting` 是「让出本轮、被输入唤醒」。本轮把 notice 归并到后者。

## 先说清三条约束（决定了形状）

- **一个 service 同时只有一个活动 task，且 `waiting` 也算活动 task**。阻塞式 notice 让那个 task 在用户回话前一直占着节点；`wait: false` 只是把问题绕开（纯记录），代价是「要人拍板」的 notice 没法再收到答复。
- **`task_inbox` 已经是唯一的输入通道**：父子消息（`message`）与子 task 结算（`child_settled`）都在同一张表、同一套 park/wake 语义（`core/tasks/messages.js`）。notice 的答复只是第三种输入，没有任何理由另造一条等待原语。
- **「这个 task 还在跑吗」不能只看 agent**。agent 结束一轮不等于 task 结束：它可能还在等子 task（`waiting`），也可能还在等用户（本轮新增 `awaiting`）。运行期决定「park 还是 settle」时必须把「有没有未决的 wait notice」算进去。

## 备注

- 改了 schema、`src/agent/guide.js`、`src/cli/tree/*`、`templates/**` 与运行期代码 → fingerprint 会变；照例 `bun run daemon-restart`。**老 home 走 v9 迁移**（`tasks` / `task_inbox` 重建），迁移前建议先备份 `$LUSH_HOME/lush.db`。
- notice **仍然不超时**：没人处理就一直 `open`，task 也一直 `awaiting`。这是刻意的（要人做的事不该被机器超时掉），收场手段是 `answer` / `dismiss`，或取消那个 task（`finish` 会把未决 notice 一并 `dismiss`）。
- `completed` 的 task 只可能剩下 `wait: false` 的 notice：`wait: true` 的 notice 在答复回来之前，运行期根本不会把那个 task 算成跑完。
- `call --interactive` 那条路（终端里的 pi TUI）不走 daemon 的 park 循环，`settleInteractive` 仍是权威出口；它不受本轮新增的 `task_complete` 拒绝影响（那个 guard 只在 agent 工具里）。
