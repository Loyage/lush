# 新手教程：完成你的第一个任务

本文面向懂基本 Git、第一次使用 Lush 的开发者。我们用“补全项目 README 的运行说明”走一遍浏览器操作；读完后，你应能发出任务、跟进执行、审阅成果，并区分合并与验收。不需要先学 CLI 或多 Agent 调度。

阅读路线：[项目概览](../README.md) → **新手教程（本文）** → [指令交付流程](task-flow.md)。还没安装也可以先读概念，再按第 2 节准备环境。

## 1. 先建立一个简单的理解

把 Lush 想成围绕 Git 项目组织工作的开发台，而不是一个只返回文字的聊天框。你提交“做什么”，Worker 保留这件工作的现场，Agent 在其中实际执行。

| 概念 | 在这次练习中意味着什么 |
| --- | --- |
| 项目 | 你要修改的 Git 仓库，不是 Lush 源码目录；两者可以是不同目录 |
| 指令 / Input | 你提交的原始目标，例如“补全 README 的运行说明”；产生后保留原话 |
| Worker | 承接这个目标的一份持续工作现场：目标、会话、分支、工作区与结果都与它关联 |
| Agent | Worker 中实际阅读文件、修改内容、执行检查的 AI 编码助手，如 Pi / Codex |
| 分支 / worktree | 分支记录这份工作的提交；worktree 是独立的文件目录。开始时取父分支的已提交版本，不包含你尚未提交的修改 |
| Notice | 需要你注意的消息：可能是待你回答的问题，也可能只是告知 |

页面用 `W…` 标识 Worker、`O…` 标识原始输入、`D…` 标识待决问题、`N…` 标识告知。它们不是同一个编号；追加要求也不是改写原始 O 输入。

**父 Worker 与子 Worker**表示工作归属和交付方向。第一次从默认 `main` 创建即可；Agent 若拆分工作，会创建自己的子 Worker。子成果先进入直接父 Worker，不等于已经进入 main，你不需要预先手工建立一棵树。

## 2. 准备并打开项目

### 还没有可用的 Lush 页面

先按你的环境选择[部署说明](deployment/README.md)：macOS / Linux 本机、远程 Host 或 Windows WSL2。安装与认证的具体命令集中在部署文档，本文不另复制一套配置。

开始练习前，确认四件事：

- 后台机器已有 Bun 1.2+、Git、Lush 源码和可用的 Pi / Codex；目标项目是**已有初始提交的 Git 工作区根目录**。
- 你知道 Host 页面地址和登录账号。本机也必须预先配置登录，没有默认密码或首次设置页。
- 编码 Agent 所需的模型来源和认证已就绪。打开页面不代表模型一定可调用；真正提交任务可能产生模型费用。
- 练习所需文件已经提交到选定父分支。先查看自己的 Git 状态，自行决定如何处理未提交改动，不要为了启动而丢弃它们。

Lush 不是沙箱，Agent 使用后台用户的系统权限。第一次请选择你信任、范围小且容易审阅的项目；不要把密钥写进指令或提交进仓库。

### 已经能登录工作台

1. 打开「项目管理」，在「项目目录」填写后台机器上项目的**绝对目录**，点「在新窗口打开」。若已登记，直接打开已有项目；单项目部署则进入所绑定项目。
2. 在打开的项目标签中核对项目名称和目录。远程访问时，这个路径属于服务器，不是浏览器所在电脑。
3. 在全局工作台的「模型来源」与「Agent 配置」核对可用来源、后端和默认模型。已有正确配置无需重配，第一次也不用安装额外插件或 Skills。

默认的 **Lush 配置**需要绑定托管模型来源；如果使用 **Pi 默认配置**，这是显式选择，使用的是后台机器用户的 Pi 环境。两条路线及登录方式见[Agent 配置说明](reference/agent-configuration.md)，不要把“软件已安装”当作“模型认证成功”。

**检查点：**你能看到正确项目的「项目树」，且知道本次会使用哪个 Agent / 模型。全局工作台用于项目入口和共享配置，项目标签用于这份仓库的工作；关闭标签不会停止后台。

## 3. 提交第一个小任务

在项目页点击右下角输入入口，选「新建工作」，核对去向是默认 `main`。第一次不设置执行条件、独占或自动验收；无需使用「管理 Lush」（它面向项目管理操作，不是普通代码开发）。

可以把下面这段作为起点，按你的项目改写：

> 请检查本项目已有的 README 和运行脚本，在 README 中补全“本地运行与验证”说明，让第一次接手的人知道需要哪些环境、如何启动、如何执行检查。只改 README，不修改业务代码或依赖配置，不安装依赖、不启动长期服务。命令必须有仓库依据，不确定的前提先问我；完成后检查文档与命令是否一致，说明实际做过和没有做过的验证，不要自动合并或验收。

这条指令给出了**目标、范围、约束和完成标准**。比“帮我优化项目”更容易执行和审阅。练习会真的修改文件，但先在 Worker 自己的工作区内，不会仅因提交输入就改动 main。

- 只想先记下来：点「保存草稿」，不创建 Worker、不调用 Agent。
- 决定执行：点紫色「提交」按钮。Enter 是换行；Ctrl/⌘+Enter 才是提交，Ctrl/⌘+S 保存草稿。
- 想查看完整去向或本条运行设置：打开「详细编辑」；不要为了看设置另建一条相同指令。

**检查点：**先查看提交收据。提交表示已授权，不保证立即开始；若正在等待安全条件，保留收据即可，不要反复提交。实际创建后，从收据提供的入口或「项目树」打开对应 Worker。尚未创建时可在「草稿」查看状态；已发送原话可从「历史输入」找回，详见[输入与草稿](input-history.md)。

## 4. 跟进工作：看结果、答问题、补要求

打开 Worker 后，先看当前状态与目标，再按需阅读对话。点「打开工作台」会在新标签页显示执行记录，也可切换到代码与改动。工具记录能帮助你区分“Agent 说打算检查”与“已经执行了检查”；结果报告也应说明改了什么、如何验证、有哪些限制。

| 看到的情况 | 你可以怎么做 |
| --- | --- |
| 正在运行 | 阅读进度与执行过程，不必守着页面；后台会继续工作 |
| 有待决问题 | 打开对应问题，阅读选项和影响后回答；关闭或忽略不等于同意推荐项 |
| 等待中 | 先看原因，可能在等你的决定、子 Worker 或下一条需求，不一定是失败 |
| 返回结果或待验收 | 开始审阅；不要仅凭这个状态判断代码已合并 |
| 失败、暂停或阻塞 | 读清错误与原因，再决定修正配置、继续或重试，不用删除状态目录排错 |

如果想补充范围，在**这个 Worker**里点「追加输入」，例如：

> 请把 README 中运行命令的执行目录写清楚，并区分启动应用与运行检查。仍然只修改 README。

追加会继续原有工作，不必新建相同任务，也不改写最初的指令。消息在 Agent 两轮执行之间交付；正在运行或合并期间显示已保存／已入箱，并不表示 Agent 已经读到。普通暂停中的 Worker 还需要显式开始／继续。

若 Agent 派出子 Worker，可以查看它们，但先围绕最初的 Worker 跟进整体结果；它负责检查子成果并汇总。你不需要逐个手工合并或验收派生 child。

## 5. 审阅、合并、验收：分三步做

### 先审阅成果

从 Worker「打开工作台」进入代码与改动视图，对照最初目标检查：是否只改了 README？命令是否对应真实脚本？前置条件是否清楚？再读验证报告，确认哪些检查**实际跑完**，哪些只是推断或尚未验证。文档检查通过不等于应用已成功启动。

不满意就追加具体要求，等新的结果后再看本轮改动。不要为了继续开发先点验收。

### 再把代码合入项目

用户新建的指令默认不自动合并。本练习保持手动路线：成果就绪后，在 Worker 详情或项目树提供的「合并」操作中确认目标分支与影响，再提交请求。

请求成功不等于已经落地。等待本轮显示**已合并**，核对目标是 main 和对应提交，才可认为这次 README 改动已经进入项目。如果出现分歧，系统会让原 Worker 在自己的工作区修复并验证；有新问题时需要你回答。

合并后仍可以向未验收的 Worker 追加需求；新一轮改动要重新审阅并交付，上一轮的“已合并”不证明这轮也合入了。自动合并只是另一种授权方式，第一次不必开启，后续见[自动化说明](hooks.md)。

### 最后验收并归档

确定这件事做完、没有后续修改需求后，点击「验收」并核对提示。**验收表示你不再有异议，同时归档并安全回收 Worker 的工作区和本地分支，保留结果、会话与历史。**它不会再请 AI 替你做质量评审，也不撤销已合并代码；已归档后有新需求应另发指令。

已交付的派生子 Worker 可随父 Worker 一并安全验收，不要求你逐个操作。若有未处理输入、待决、未交付改动或资源回收失败，按提示处理，不能把“点过按钮”当作验收完成。

| 事实 | 它证明什么 | 不证明什么 |
| --- | --- | --- |
| Agent 返回了结果 | 本轮调用给出了报告 | 改动正确、测试通过或已进入 main |
| 本轮已合并 | 本轮提交已进入指定父分支 | 所有用户要求已满足、后续改动也已合入 |
| 验收成功 | 你确认结束，安全归档回收已完成 | 自动做过质量评审或删除了运行历史 |

如果任务只是解释代码、没有任何新提交，就不需要合并；检查答案满意后仍可验收，回收那份工作现场。

## 6. 第一次使用的常见卡点

| 问题 | 先检查什么 |
| --- | --- |
| 页面打不开或不能登录 | Host 是否运行、地址是否正确、登录配置是否已准备；按[部署说明](deployment/README.md)排查，不找默认密码 |
| 页面打开了，Agent 却不能运行 | 软件可用性、模型来源认证、所选模式和账号额度；页面与模型是两条不同链路 |
| Worker 看不到我刚改的文件 | 它基于创建时父分支的已提交版本，不读取你后来或尚未提交的本地编辑 |
| 提交后没有立即出现 Worker | 查原收据与草稿的等待／错误信息；结果未知时先核验原请求，不另发一份 |
| Agent 说完成，main 却没变化 | 查本轮是否真的已合并，以及合入的是不是 main；子 Worker 可能只合入它的父 Worker |
| 合并或验收按钮不可用 | 看提示中的阻塞原因；不要强删分支、工作区或 `.lush/` 绕过检查 |

需要报告问题时，带上项目、Worker 编号、原始错误和你刚做的操作，不要粘贴密钥或登录凭证。需要安全中断或更新服务时，另读[项目维护](project-maintenance.md)，不要把关闭浏览器当成停止执行。

到这里，你已经能独立完成一次“小目标 → 执行 → 审阅 → 合并 → 验收”。接下来再按需学习草稿、自动化与多 Worker 协作，不必一次掌握全部设置。
