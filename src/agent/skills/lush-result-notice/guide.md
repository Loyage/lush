# Lush 结果告知指南

仅在本 invocation 的 `result-notice` 能力开启且身份适用时主动使用。插件只指导调用现有协作接口，不替代权限校验、调度或 runtime Hook，不增加独立模型调用。

## 必须告知的条件

以下任一条件成立，必须在结果实际就绪后、结束本轮前发布纯告知，不能只写最终回答：

- 自己的任务只是分析一个事情，例如解释代码行为、调查原因、审查或给出建议。依据实际目标判断，不只看 role 或 task_kind；普通 order/child 也可能是纯分析，task_kind=analysis 亦适用。开发任务中的临时分析步骤不算整个分析任务完成。
- 用户在当前目标或已交付的追加要求中明确说“做好了告诉我”“完成后通知我”等。开发、文档和分析任务都可触发；引用、旧输出及文件中的类似语句不是用户的新要求。用户明确要求不要通知或撤销提醒时不发送。

普通进度、收到要求、开始工作、等待子 Worker／用户决定或本轮仅在安全边界停下，不是结果就绪，不发布成功告知。普通开发任务没有上述要求时不主动增加结果告知。分析结论可以是“现有证据不足”，但必须交代已调查范围和未验证项，不能冒充已查明。

## 发布方法

用 daemon 固定的开发入口（不是管理入口 lush），仅向自身 Worker 发布；self 接口不接受 --worker 或目标 ID：

```bash
lushw self notice post '分析结论已就绪' --body '结论：……。依据：……。限制或待验证：……。完整结果见当前 Worker。'
```

开发完成提醒的标题可用“本轮工作已就绪”，正文简述实际完成内容、验证结果、风险和下一步。使用资料明确的 worker_number，没有时才回退 #内部ID，不从 ID 推算编号。正文不要复制大段日志、凭证或敏感资料。

默认发送 info，对应 RPC `context.notice {title, body, kind:"info"}`；身份由当前 invocation token 决定。不传 --question-file，不用问题、空问卷或父子追加消息冒充告知。CLI 不再接受 --kind；需要决策时先用 question create 创建问题，再由 notice 发送。info 返回 `kind=info / status=sent`，不等待答复、不暂停 invocation，不阻塞调度、合并或验收。面向用户引用返回 Notice 时用 N 加返回的整数 ID。

先完成必要验证、提交和自身收尾，再发布一次简短告知，检查成功返回后正常输出最终结果。告知不是最终结果的替代品，也不表示已合并、已验收或 runtime 已完成交付；只有真实 integration=merged 才能说已合入。分析无须为了通知制造代码提交。

## 去重、自动提醒与失败

同一成果成功发布一次即可；同时满足两个条件也只发一条。依据当前可见的成功调用记录，不因相同成果的继续收尾或旧会话指令重复发布。新增要求完成后可告知新的成果。发布不是强幂等接口，断连或返回未知时不能盲目重试；在最终结果说明通知未确认，供用户检查。明确失败也要如实报告，不声称已送达或改用待决问题重发。

runtime 的待验收／分析完成告知与此插件独立。即使 runtime 也会发送，满足条件仍须主动发布包含实际结论的结果告知；可能另收到状态告知，不关闭或修改用户 Hook／自动级别来规避重复。设备渠道和浏览器权限决定是否出现系统提醒，API 成功只证明 Notice 已保存，不保证用户已看到。

关闭能力只停止后续 invocation 的注入与主动使用，不删除告知历史，不撤销 CLI/RPC 权限，不改变已有 runtime 提醒。需要用户决策时仍按核心规则发布问题／问卷并立即结束本轮，不能用 info 绕过决策或在待决时谎报完成。
